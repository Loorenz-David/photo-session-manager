# Backlog (reviewer notes that did not block)

| Phase | Note | Why it matters |
|---|---|---|
| P00 → P04, P16 | `health_get` is a sync Tauri command that runs the Capture One probe (`OsaRunner`, 30 s timeout) inline while holding the `Mutex<App>`; sync commands execute on the IPC dispatch thread, and the JXA `Application("Capture One")` call launches Capture One when it is not running. | While Capture One is busy, launching, or the Automation prompt is up, the window can freeze for up to 30 s and every other command waits on the lock. Provider calls from commands should be `async`/off-thread and must not hold the app lock (P04 adds many). |
| P00 → P16 | The `capture_one` health item is assembled inside the `health_get` command (probe call + ok/detail mapping) rather than in `HealthService`. | H8 says commands are thin; the phone remote would have to duplicate it. Move it into the service when P16 adds provider health items. |
| P00 → P06, P16 | `Settings::open` returns an error (and `run()` panics at startup) when `preview_delay_s` is not an unsigned integer or `settings.json` is malformed; MC-17 says "missing or not a number → 15 s". | A hand-edited settings file stops the app from starting instead of falling back to 15 s. P06 consumes the delay; P16 owns settings validation. |
| P00 → P01/P05 | Spool dedupe keys are stored as one `settings` row per consumed hook file (`spool:<name>`), forever. | Unbounded growth of the app-state key/value table (a row per render and per edit). Prefer a UNIQUE `spool_name` column on `capture_events` in a new migration (never rewrite `001_init.sql`). |
| P00 → P05 | The hook templates' AppleScript `jsonEscape` escapes `"`, `\`, CR, LF and tab only; MC-15 requires all control characters. | A path with any other control character yields invalid JSON → `spool/bad/` → the event is lost (M22). Rare in practice, but P05 dispatch relies on it. |
| P00 → P05 | If `FsWatcher::watch(spool)` fails, the background thread returns and also stops the 5 s interval drain. | MC-15 lists four independent drain triggers; one failing should not silence another. |
| P00 → P16 | `logging::init` runs after `App::open`, so the startup drain, hook compilation and probe-script write are never logged. | Diagnosing a failed startup from the log file is impossible. |
| P00 (test) | `c1a` asserts `settings["document_id"]` and `settings["integration"]` equal `null`, which `serde_json` indexing also returns for an absent key. Production writes both keys as `null` (verified by reading `Settings`). | The row says "containing every key"; the test cannot tell absent from null. No user-visible effect today. |
| P00 → before P07 | Spike items still open: (c) the Automation prompt from the bundle with the real-event probe, and remembered on relaunch; (f) launch on the work Mac; (e) FSEvents on the real capture folder (P05). | Ch11 asks for the spike outcome before any UI phase. (c) needs the owner's hands. |
| P00 | `apps/desktop/src-tauri/icons/SessionManager.iconset/*` is left over from the failed `iconutil` attempt and is not referenced by `tauri.conf.json`. | Dead files in the repo. |
| P01 → P05, P13, P16 | `IntegrityCheck::verify` reports `raw_changed` when the photo has no `raw_hash` yet (`None != Some(actual)`). No caller exists in P01. | MC-3's checks (prepare, health) run on photos whose hash job may not have finished; such a photo would be wrongly marked changed and its publish blocked. The caller must hash first or treat a missing hash as "pending", not as a mismatch. |
| P01 → P03 | The built-in Unassigned session is stored with `created_at = last_activity_at = 0` (1970-01-01). | MC-4 grouping by `last_activity_at` would put Unassigned in a "January 1970" month group unless P03 places it separately or an arrival bumps it. |
| P01 → master plan §6.6 | `CommandError.code` can be `not_found`, `io`, `invalid_data` or `provider`, which are not in the §6.6 error-code registry. | The frontend switches on codes; unregistered codes will be handled ad hoc per phase. Register them (or map them) when the first UI phase (P07) consumes errors. |
| P01 → P07 | `items.title` and `items.item_type` are `NOT NULL` and `create_local` requires both, while ch05 lists only `sku` as required. | P07's "Create '…'" row in New session must supply a title and type (or the schema relaxes in a new migration); otherwise creating an item from a bare SKU fails. |
| P01 → P02/P03 | The suggested `mark_published(session, seq)` testkit helper was deferred (no P01 caller, §7.5). | The first phase that needs a published session (P02 move/copy refusal or P03 status) must add it. |
| P02 → P07, P08 | The six review commands return the touched sessions' DTOs but emit no `session_changed` / `photo_changed` event (master plan §6.7 registry). | P07's sessions list refreshes only on `session_changed`/`photo_added`; a classify, delete or move made in the workspace would leave the list's counts, dirty state and `last_activity_at` ordering stale until something else fires. Emit from the command layer or the service's event port when the UI phases wire these up. |
| P02 → P08 | A move/copy batch in which two selected photos share one RAW (e.g. a photo and its copy from another session) is refused as `target_has_raw`, although the target holds no row on that RAW. | Refusing is right (the target would get two rows on one RAW), but the UI text for `target_has_raw` ("already in that session") would be wrong for this case; P08 should word the toast to cover it or the service should use a distinct code. |
| P02 | `copy_photos` gives the new row the source row's `created_at` instead of the copy time. | `created_at` of the copy misreports when the row was made; nothing orders by it today, so no visible effect. |
| P03 → P07 | `unassigned_count` is the Unassigned session's `photo_count`, which also counts photos marked deleted. | The design shows the Unassigned card "only when unassigned photos exist"; a bucket holding only hidden photos would still show a card with a non-zero count. Count non-deleted photos (or let P07 decide what the card counts). |
| P03 → P07 | The `sessions_list` row DTO carries flat `main_count`, `condition_count`, `unreviewed_count`, where C5(a) wrote `counts{main, condition, unreviewed}`. | Same data, different shape. P07 should build against the generated binding as it is, not the plan's notation. |
| P03 | `session_list_records` runs about four queries per session (session DTO, missing previews, cover, latest publish item). | Fine at the hundreds of sessions the MVP expects; a single grouped query would be needed only if the list grows to thousands. |
| P03 | A `last_activity_at` later than now (Mac clock moved back) is grouped as "This week" or a month, never "Today". | Rare. A session would look older than it is until it changes again. |
| P03 → P13 | In `c1l_latest_confirmed_wins` the run inserted later also has the later `confirmed_at`, so the test cannot tell "latest by confirmation time" from "latest by run id". The SQL orders by `confirmed_at` first (correct today). | If P13 lets a run be created before another but confirmed after it, a regression to id order would go unseen. P13's publish tests should include one run confirmed out of creation order. |

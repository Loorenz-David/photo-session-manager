# Backlog: H3_bring_back (reviewer notes; notes never block, flow.md §5)

- **H3 reviewer r1 (note → H4, M-H2): a failure after the import commits would delete the files it just imported.** In `services/bring_back.rs`, `bring_back_running` calls `self.leave_gone(item_id)?` after `Store::bring_back` has committed. If it returned an error, `bring_back` would run the failure path anyway: `written.remove_all()` deletes the five new files, and it emits `BringBack {Failed}`, while the photo rows, links and `restored_at` are already stored. The item would then be `Local`, with rows naming files that no longer exist, and could not be brought back again. Today `leave_gone` can only fail on a poisoned mutex (`lock_gone`; `health.set` returns nothing), so a user cannot reach this. Why: the next post-commit step someone adds with `?` makes it real. Every step after the transaction should log its error, never return it.
- **H3 reviewer r1 (note → H4, MC-H4.1): the remote-state check happens before the running mark is taken.** A second press can pass `state == Remote` while the first bring back is still running. If the first then finishes and drops its mark before the second reaches `start_running`, the second runs a full bring back of a now-`Local` item. It downloads everything again under `-b2` names and retires the photos the first one just imported. The window is microseconds wide (H3·C7(c) covers the ordinary overlap). Why: H4's button and command should keep the press disabled while a bring back runs, or `bring_back_running` should check the state again after taking the mark.
- **H3 reviewer r1 (note → book 10H §7.1): a file at a target name that no photo row names is overwritten, and deleted if the attempt fails.** MC-H4.3 treats every such file as "a leftover of an interrupted attempt". It cannot tell that from a file the owner put there by hand under the same name (`<SKU>-main-01.jpg`). The risk is low because the names are the app's own pattern. H2's exception wording ("only the files that attempt itself downloaded") covers it only loosely.
- **H3 reviewer r1 (note → H4): `Store::bring_back` retires every photo row of the session at commit time.** Suppose a RAW is filed into the session between the moment the bring back starts and the import (the session is active and something arrives in its folder). That photo would be retired too: hidden, `raw_missing`, its file still on disk (not deleted, so H2 holds). Before H4 this cannot happen, because a remote session is never active. H4 adds activation after bring back and should keep the session from taking arrivals while a bring back runs.
- **H3 reviewer r1 (note, H7 family): `Store::bring_back` adds one more hard-coded `'shopify'` literal** in its `photo_links` insert (`crates/infra/src/sqlite/store.rs`), as every existing photo-link query in that file already does. It is in infra and writes a link table, so H7 holds. It joins the known "H7 family" debt in `backlog.md`.
- **H3 reviewer r1 (note, plan hygiene): U2's Files list names `crates/testkit/src/test_app.rs` and `apps/desktop/src/services/bindings.ts`, and neither changed.** The fake shop's `RemoteItems` is built by `App::build` with the same uncached capture-root closure, and no specta type changed. The handoff's declared perimeter matches the commits exactly. Why: a later perimeter check should not read these two paths as missing work.
